# 02 · 坐标与截图

> 状态：**讨论中（D5）** · 草案 v0.1
>
> 本章只解决一个问题：**AI 在图上量的那个框，怎么变成屏幕上那个框。**
> 这是整个产品最容易翻车的地方——坐标错了，遮罩再漂亮也是错的，而且用户会立刻不信任它。

## 1. 三个坐标空间

```
 ① 图像像素 (image px)          ② 逻辑像素 (dip / point)        ③ 物理像素 (screen px)
 AI 在截图里量出来的               UI 框架、字体、间距              窗口、合成器、显示器
        │                              │                              │
        └────── capture.mapping ───────┴──────── DPI scale ───────────┘
```

| 空间 | 谁在用 | 陷阱 |
| --- | --- | --- |
| image px | AI、截图文件 | 截图可能被工具缩放过，也可能拼了多屏 |
| dip / point | 一般 UI 代码 | 125% 缩放下 1 dip = 1.25 px，四舍五入会漂 |
| screen px | Win32 / CoreGraphics 的真实坐标 | 多屏原点可能是负数 |

**设计原则：`spotlight-core` 内部只认 ③（物理像素、左上原点、y 向下）。**
其余两种空间只在边界出现，且必须显式携带换算依据。

## 2. 契约：图像像素 + capture 引用

> **D5a 决策（2026-10-19）**：采用"强制二选一，不给就报错"。不提供聪明的默认值。

`show` 的坐标**必须**二选一，不能猜：

| 输入 | 含义 | 场景 |
| --- | --- | --- |
| `--capture c-7` | 坐标是 c-7 这张图的像素 | **推荐路径**，零歧义 |
| `--space screen` | 坐标就是物理像素 | 逃生口：AI 自己截的图、或写死的坐标 |

两个都不给 → 报错，并给出下一步怎么做：

```json
{"ok":false,"error":"space_unspecified",
 "hint":"坐标空间未指定。请先运行 spotlight capture 拿到截图，再用 --capture <id> 传坐标；或显式指定 --space screen 表示坐标已是屏幕物理像素。"}
```

> 为什么强制二选一：如果给一个"聪明的默认值"，它总会在某个 DPI 组合下猜错，
> 而猜错的表现是"框偏了 30 像素"——用户只会觉得这软件不准，不会觉得是配置问题。
> 宁可第一次调用失败，也不要静默地错。

## 3. capture 的输出

```jsonc
{
  "ok": true,
  "capture": "c-7",                          // 后续 show 引用它
  "image": { "path": ".../spotlight/c-7.png", "format": "png",
             "width": 1280, "height": 720 },
  "monitors": [
    { "index": 0, "name": "\\\\.\\DISPLAY1", "primary": true,
      "bounds": [0, 0, 1920, 1080],          // 物理像素，左上原点，已归一化
      "work":   [0, 0, 1920, 1040],          // 去掉任务栏
      "scale": 1.25 }
  ],
  "segments": [                              // 图 与 屏 的分段对应关系
    { "monitor": 0, "image_rect": [0,0,1280,720],
      "screen_rect": [0,0,1920,1080], "scale_x": 1.5, "scale_y": 1.5 }
  ],
  "virtual_screen": { "x": 0, "y": 0, "width": 1920, "height": 1080 }
}
```

换算（这就是 `spotlight-core` 里唯一的一段坐标数学）：

```
screen_x = seg.screen_rect.x + (img_x - seg.image_rect.x) * seg.scale_x
screen_y = seg.screen_rect.y + (img_y - seg.image_rect.y) * seg.scale_y
```

- 用 `round()`，不截断；并且**渲染用同一份换算结果**，避免"框和文字各算一遍导致差 1px"。
- 显示器排列在 macOS 上可以是任意角度（上下左右都有），所以 `segments` 里必须能表达
  "图上的左半边对应屏幕的右半边"这种情况——`image_rect` / `screen_rect` 各自独立，
  不假设方向一致。

## 4. capture 的规格

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 谁来截 | **Spotlight 自己截**（D5 倾向，待确认） | 只有它知道自己的 DPI 认知，也才能保证 mapping 与渲染用的是同一套枚举结果 |
| 存哪 | `%LOCALAPPDATA%\spotlight\captures\c-<n>.png`（mac 为 `~/Library/Caches`） | 不污染用户目录 |
| 留住多久 | 最近 20 张，或 10 分钟 | 防止无限增长 |
| 默认范围 | 主显示器 | AI 一开始总是从用户当前焦点说起 |
| 多屏 | `--monitor N` 单屏；`--all` 拼成一张并给出多段 mapping | 拼图时坐标语义仍然清晰 |
| 缩放 | `--max-width` 默认 1280（D10 待定） | 大图对模型是纯 token 浪费，且不影响精度——精度由 mapping 兜住 |
| 格式 | PNG；`--format jpeg` 可换（体积换画质） | 截图要能看清小字 |
| 前一步 | **截图前主动隐藏所有遮罩，等一帧，再截** | 不依赖 `WDA_EXCLUDEFROMCAPTURE` 在每个版本上的行为一致性 |

> 关于缩放：`--max-width` 让图片变小，但 `scale_x` 会同步变大（例如 1.5）。
> AI 在 1280 宽的图上量 32px 的按钮，换算到屏幕是 48px——**正确**，因为按钮在屏幕上
> 确实占 48 物理像素。这正是不让模型自己换算的价值。

## 5. 如果 AI 用的是自己截的图

这是常见情况（很多 Agent 有自己的截图工具）。三条路，按推荐度排：

1. **改用 `spotlight capture`** —— 零成本，最稳。
2. **`--space screen`** —— AI 自己保证坐标是物理像素。适合图与屏幕 1:1 的场合。
3. **`spotlight calibrate --image shot.png --json`** —— 给定一张图，按宽高比匹配到
   某个显示器，算出 scale 并返回 mapping。匹配到多块屏时会**报歧义**而不是乱猜。

第 3 条只做"尺寸匹配"这一种推理，不做图像特征匹配——后者不可解释，出了错没人能查。

## 6. DPI 与多屏的实现要点

**Windows**

- 清单文件声明 `PerMonitorV2`（`<dpiAwareness>PerMonitorV2</dpiAwareness>`）。
- **绝不调用** `SetProcessDPIAware`（V1 API），它会把进程降级，之后 `GetSystemMetrics`
  返回的值全是虚拟化的，坐标从此不可信。
- 每个显示器一个 overlay 窗口，窗口落在哪块屏就用哪块屏的 DPI。**不做跨屏单窗口**。
- 收到 `WM_DISPLAYCHANGE` / `WM_DPICHANGED`：不试图平滑迁移，直接"隐藏 → 重新枚举 →
  重算 → 重画"。一帧的闪动远好于坐标错乱。
- 获取显示器矩形用 `EnumDisplayMonitors` + `GetDpiForMonitor`（或
  `GetDpiForWindow` + `GetWindowRect` 交叉校验）。

**macOS**

- `NSScreen.frame` 是**点**，且全局原点在主屏**左下**、y 向上。Windows 是左上、y 向下。
- 换算集中在 `spotlight-mac` 的边界函数里：`(px, py) -> (point_x, primary_h - point_y - h)`。
- 位图按真实像素渲染（如 400×100 px），塞进 layer 时 `contentsScale = backingScaleFactor`，
  尺寸按点算（200×50 pt）——这样 Retina 上不会糊。
- 外接屏与内置屏的 `backingScaleFactor` 可能不同（2x / 1x），必须**逐屏**取。

**共同点**

- 多屏摆放可以是负数坐标（副屏在主屏左边 → x < 0；在上边 → y < 0）。所有内部矩形
  都用有符号 int32，不用 u32。
- "屏幕拼接后的大矩形"只用于判断越界，不用于创建窗口。
- **遮罩按显示器分别生成**：目标在哪块屏，就只压暗那块屏；跨屏目标会各自压暗所在屏，
  而不是把整个虚拟桌面涂黑。
- 目标归属哪块屏，按"重叠面积最大"判定（`monitor_for_rect`），不要求完全包含——
  否则压在屏幕边界上的目标会被判成越界。

## 7. 越界与容错

| 情况 | 处理 |
| --- | --- |
| 矩形完全在屏幕外 | 退出码 3 + 列出每块屏的 bounds（让模型自己修） |
| 矩形跨两块屏 | 默认裁到重叠面积最大的一块并 `warn`；`--strict` 则报错 |
| 矩形小于 8×8 | 视觉上按最小 24×24 居中放大，但**不改**逻辑上的 target（点击观察用的是原矩形） |
| 矩形极大（> 80% 屏幕） | 允许，但气泡自动改为"屏幕居中"布局 |
| `--padding` | 默认 6 px（物理像素，不随 DPI 变），光环画在 target 外扩后的位置 |

不做自动 clamp（把越界矩形拉回屏幕内）——那会画出一个"看似合理但错了"的框，
比报错更糟。`--clamp` 作为显式选项保留给"差一点"的场景。

### 一个可能的增强（v1.1 再议）

Windows 的 UI Automation 可以把一个粗糙的矩形**吸附**到真实控件的 bounds 上：

```bash
spotlight show --rect 810,130,40,40 --snap uia
```

好处：AI 只需要"大概在哪"，精度由系统给。代价：UIA 在某些应用上很慢（100ms～1s）
甚至卡死，必须带超时和 fallback。**不进 v1**，但值得把参数名先留出来。
